# Gateway Week One validation

This harness validates real governed requests and records an unchanged production baseline for Task 1. It creates disposable applications, resources, a provider, and policy in an isolated test zone through the Admin API. SDK requests use the actual Coordinator, STS, Gateway, PostgreSQL, Redis, and Audit services. Only the upstream service is controlled test code.

The `api_key` provider contains a random test-only key. The upstream reports whether Gateway injected that key and stripped reserved routing headers. Tokens and credentials are never written to result files. A local control endpoint records upstream executions so denial tests can distinguish a blocked action from an error returned after execution.

## Prepare the stack

From the repository root, install the repository's locked dependencies and build the TypeScript packages, then start the local development services:

```powershell
pnpm install --frozen-lockfile
pnpm run build:typescript
pnpm caracal up --wait postgres redis sts api coordinator gateway audit
```

Use the source-built Node image tag printed by the workspace CLI. For the Week One baseline at commit `7d5602d7c`, the controlled upstream was started with:

```powershell
docker run --detach --name task1-upstream --label caracal.task=week-one `
  --network caracalDevData --publish 127.0.0.1:18080:18080 --env PORT=18080 `
  --read-only --cap-drop ALL --security-opt no-new-privileges `
  --mount "type=bind,source=$((Get-Location).Path)\tests\shared\mocks\gatewayWeekOneUpstream.mjs,target=/week1-upstream.mjs,readonly" `
  localhost/caracal-node:1.0.0-dev.sha7d5602d7c /week1-upstream.mjs
```

The upstream uses the existing image's non-root Node entrypoint and health check. Its control port is published only to loopback. Keep it on the same development network as Gateway. Other operating systems can use the same image and fixture with their native absolute bind-mount syntax.

If the fixture container already exists from this investigation, use `docker start task1-upstream` instead of creating another container with the same name. After the recorded Week One runs, the test containers were stopped to avoid leaving the large audit backlog consuming the host indefinitely. Containers and development volumes were retained. Restarting the stack resumes that existing dataset; it does not provide a clean-database baseline or establish that the audit replay backlog has converged.

Set local service URLs when the defaults differ. Supply paths to the development secret files generated by Caracal; never paste secret values into commands or reports. On the measured Windows host, the existing development secret directory was `%LOCALAPPDATA%\caracal\dev-secrets`:

```powershell
$task1SecretDir = Join-Path $env:LOCALAPPDATA 'caracal\dev-secrets'
$env:CARACAL_ADMIN_TOKEN_FILE = Join-Path $task1SecretDir 'caracalAdminToken'
$env:CARACAL_COORDINATOR_TOKEN_FILE = Join-Path $task1SecretDir 'caracalCoordinatorToken'
$env:CARACAL_METRICS_TOKEN_FILE = Join-Path $task1SecretDir 'metricsBearer'
$env:CARACAL_WEEK1_REDIS_URL_FILE = Join-Path $task1SecretDir 'redisUrl'
$env:CARACAL_E2E_UPSTREAM_URL = 'http://task1-upstream:18080'
$env:CARACAL_WEEK1_UPSTREAM_CONTROL = 'http://127.0.0.1:18080/__control'
$env:CARACAL_WEEK1_COMPOSE_PROJECT = 'caracal-dev'
```

## Run correctness checks

```powershell
$env:CARACAL_WEEK1_MODE = 'correctness'
$env:CARACAL_WEEK1_OUTPUT = '.tmp/task1/correctness'
pnpm test:gateway:week1
```

To include dependency failures, use the following command only on a dedicated local stack whose services can be interrupted:

```powershell
pnpm test:gateway:week1 --faults
```

Fault tests require an explicit Compose project. They locate exactly one running container for each dependency, stop/restart only those containers, and attempt recovery in `finally` blocks. They verify readiness across services and a real governed request after recovery. Do not run them against a shared or production stack.

The matrix covers allowed calls, provider credential injection, audit correlation, invalid credentials, signature forgery, replay, expiry, wrong resource/scope/operation/zone, encoded traversal, unsafe upstream addressing, upstream failures/redirects/timeouts, request size, cancellation, Session/Delegation revocation, streaming, policy changes, concurrent applications, and dependency outages.

The stream investigation uses a 10-second threshold, not an established product SLO. It continues observation for up to 75 seconds to characterize delayed propagation. An SDK error during post-revocation cleanup is preserved even if the denial assertion in the callback succeeded. Result details separate those outcomes.

The final matrix also exercises a quiet event stream that emits one chunk and then waits. After suspension closes the stream, it resumes the same Session and checks that a fresh call succeeds. The Delegation case verifies that the parent and child share authority, checks the child's denial and SDK cleanup, then verifies that the parent can still delegate to a new child that completes a governed call.

## Run the baseline benchmark

Complete failure injection and other CPU-intensive tests before benchmarking. Keep source, images, limits, identity distribution, and data state consistent between baseline and future optimized runs.

```powershell
$env:CARACAL_WEEK1_MODE = 'benchmark'
$env:CARACAL_WEEK1_OUTPUT = '.tmp/task1/benchmark'
$env:CARACAL_WEEK1_IDENTITIES = '16'
$env:CARACAL_WEEK1_CONCURRENCY = '1,4,8,16'
$env:CARACAL_WEEK1_REPEATS = '3'
$env:CARACAL_WEEK1_SECONDS = '30'
$env:CARACAL_WEEK1_WARMUP_SECONDS = '30'
$env:CARACAL_WEEK1_SOAK_SECONDS = '600'
$env:CARACAL_WEEK1_SOAK_CONCURRENCY = '2'
pnpm test:gateway:week1
```

Each identity owns a distinct resource with the same upstream and scopes, respecting the policy data-document ownership model. Transports provision their required Sessions/Delegations before steady-state timing. Every measured call still obtains a fresh resource mandate and traverses Gateway's per-request STS exchange and governance checks. No token or response cache is added by the harness.

The measured Week One sweep uses three 30-second repetitions per concurrency level, followed by a ten-minute soak at two clients. A preliminary two-minute single-client run exposed delayed audit ingestion; its data is preserved separately. The shorter repeated sweep and moderate soak characterize the unchanged system while tracking that backlog. The harness records pending audit samples instead of treating a fixed ingestion deadline as data loss or silently aborting the sweep. It stops load if sampled Redis container memory exceeds 85 percent.

The measured stack's internal Redis `maxmemory` was 512 MiB, below that container-based guard. Redis reached this internal limit and returned OOM errors late in the soak. Policy mint quotas also caused expected denials. These results characterize overload and audit buffering; the soak is not evidence of an error-free sustainable rate. No quota, retention rule, database index or service implementation was changed for the run.

The load model is closed loop. A stalled request reduces offered load, so these measurements do not describe latency under a fixed external arrival rate. Successful RPS excludes denials and transport errors. p50/p95/p99 use nearest-rank percentiles over successful request durations; raw failures and their durations are retained separately. Stage timings measure client-side STS/Gateway response-header time, while complete-call latency includes response-body consumption. They are not CPU profiles or a complete server-side decomposition.

For a paced before-and-after comparison, use equivalent local stacks and set these workload parameters on both revisions. Use separate fresh volumes and identical limits. If a local port is in use, publish alternate loopback ports through a Compose override and set the corresponding service URL variables. Set `CARACAL_WEEK1_REDIS_PORT` when the Redis observer uses an alternate host port.

```powershell
$env:CARACAL_WEEK1_CONCURRENCY = '4,8,16'
$env:CARACAL_WEEK1_RATES = '20,40,60'
$env:CARACAL_WEEK1_REPEATS = '2'
$env:CARACAL_WEEK1_SECONDS = '25'
$env:CARACAL_WEEK1_WARMUP_SECONDS = '10'
$env:CARACAL_WEEK1_SOAK_SECONDS = '120'
$env:CARACAL_WEEK1_SOAK_CONCURRENCY = '12'
$env:CARACAL_WEEK1_SOAK_RATE = '50'
pnpm test:gateway:week1
```

With rates set, the concurrency values are caps on simultaneous requests. The harness records offered slots, missed schedules and HTTP or SDK failures separately. A missed slot indicates that the load generator was late or the cap was reached. Check each point's achieved rate and verify the stored audit events against all successful request IDs before comparing results.

The 500-request direct-upstream measurement is a sequential latency control, not an equivalent capacity test. It uses only the random fixture key and explicitly bypasses governance for that labeled control measurement.

## Evidence and interpretation

- `results.json` contains environment, scenario outcomes, benchmark configuration, per-run summaries, metrics, cleanup results, and remaining errors.
- `*-samples.json` contains raw request durations, stage timings, status/error classes, and correlation IDs. It contains no bearer tokens.
- `resource-samples.json` contains asynchronous Docker resource samples for the seven local services and the Audit consumer's Redis lag/pending counts when its observer URL is supplied. Sampling uses child processes and does not block the request loop.
- PostgreSQL cumulative statistics before/after the run help quantify dependency work. No query profiler is enabled or server configuration changed by this harness.
- The first and last successful requests of each load run are checked for correlated audit evidence. Ingestion still pending at that point is explicitly recorded. Full-run audit count reconciliation must be collected separately before claiming lossless evidence for every benchmark request.

Compare Gateway counters, upstream executions, raw samples, and database audit action counts after the evidence pipeline drains. Preserve expected-denial tests separately from throughput results. A failed test is a result to investigate, not permission to bypass its security check.

The harness cleans up through the Admin API. Cleanup failures are recorded and make the command fail. A forcibly interrupted process can leave its disposable zone; identify it by the exact `runId` and recorded zone ID before cleaning it up. Never bulk-delete unrelated zones.

Verify the measurement helper with `pnpm test:gateway:week1:tools`. All production optimizations remain outside Week One.
